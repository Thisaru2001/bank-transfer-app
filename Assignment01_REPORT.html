1. Executive Summary & Scenario Overview

A banking system demands strict adherence to consistency and data integrity. In a fund transfer workflow, money is debited from a sender and credited to a recipient. If a system failure or network disruption occurs midway through the operation—after funds have been withdrawn from the sender but prior to credit reaching the receiver—uncommitted state changes would cause funds to vanish permanently.

This project delivers a complete enterprise-grade Spring Boot full-stack banking application that implements: 1. ACID Transaction Management: Powered by Spring's @Transactional(rollbackFor = Exception.class) to guarantee all-or-nothing execution. 2. Spring Dynamic Proxy Architecture: Ensuring transactions are intercepted and managed transparently. 3. Optimized Persistence with @Query: Custom JPQL queries, native MySQL queries, and atomic @Modifying queries. 4. Independent Failure Auditing: Utilizing Propagation.REQUIRES_NEW in an isolated Spring service (TransactionAuditService) to record transaction failures in the database even after the primary transfer transaction rolls back. 5. Task 10 Transaction Isolation Experiment: Demonstrating the catastrophic financial loss caused when transaction boundaries are omitted (Propagation.SUPPORTS) versus full rollback protection. 6. Task 12 System Extensions: Supporting large-transfer thresholds, account history totals, deposit/withdrawal operations, and an atomic 1% bank fee routed to institutional account 999999.

4. Database Implementation & Entity Design

4.1 Database Engine Requirements

The MySQL database bank_db is configured using the InnoDB storage engine. Unlike MyISAM, InnoDB supports ACID transactions, row-level locking, foreign keys, and transaction rollbacks (ROLLBACK).

6. Transaction Management & Rollback Architecture

6.1 ACID Properties in the Banking Context

ACID Property Real-World Guarantee in Bank System
Atomicity All transfer steps (sender debit, optional fee credit, receiver credit, transaction logging) succeed together or fail together. Money never leaves one account without arriving at the intended destination.
Consistency The total quantity of money in the bank is conserved ($S_{total} = \sum \text{balances}$). Balances can never become negative.
Isolation Concurrent transfer operations run without dirty reads, non-repeatable reads, or phantom reads. Database row-level locks prevent conflicting balance modifications.
Durability Once a transfer is committed, the updated balances and transaction rows are written to persistent disk storage (redo log / InnoDB tablespaces), surviving application or OS crashes.

6.2 Spring Dynamic Proxy Execution Flow

When a client invokes BankService.transfer(), the request passes through a Spring dynamic proxy:

Controller ---> [ Spring Proxy Interceptor ] ---> BankService.transfer()
                     | BEGIN Transaction
                     | debit(sender)      <- UPDATE customers SET balance = balance - amount ...
                     | [Simulated Check]  <- If ticked, throws BankException
                     | credit(receiver)   <- UPDATE customers SET balance = balance + amount ...
                     | save(transaction)  <- INSERT INTO bank_transactions ...
                     |
                     |--> If SUCCESS: COMMIT Transaction (changes written permanently)
                     |--> If EXCEPTION: ROLLBACK Transaction (all balance changes undone)

6.3 Independent Failure Auditing with REQUIRES_NEW

When BankService.transfer() throws an exception, Spring immediately marks the current transaction for rollback. If the application attempted to save a FAILED record within that same transactional method, the rollback would wipe out the failure log as well!

To solve this: 1. TransactionAuditService is placed in a separate Spring service bean. 2. Its method recordFailure() is annotated with @Transactional(propagation = Propagation.REQUIRES_NEW). 3. When called, Spring temporarily suspends the outer rolling-back transaction, opens a fresh, independent physical transaction, inserts the FAILED transaction record, and commits it immediately. 4. The outer transaction then completes its rollback without affecting the audit trail.

7. Compulsory Assignment Questions & Academic Answers

Question A: What would have happened to the money in test 4 without @Transactional?

Answer:
In Test 4, a transfer of LKR 1,000.00 is initiated from Kamal (100001) to Saman (100003) with the "Simulate a system failure" option checked. Without @Transactional (such as under Propagation.SUPPORTS or with auto-commit enabled on individual statements): 1. The debit() query executes first and commits immediately to MySQL: Kamal's balance drops from LKR 50,000.00 to LKR 49,000.00. 2. The code then encounters the simulated failure and throws a BankException. 3. Because no overarching transaction coordinator wraps the steps, the previously committed debit is never undone. 4. Execution halts before reaching the credit() operation for Saman. Saman receives nothing (remains at LKR 10,000.00). 5. Consequence: The LKR 1,000.00 has completely vanished from the banking system. The bank's total assets drop from LKR 85,000.00 to LKR 84,000.00, violating Atomicity and Consistency. With @Transactional(rollbackFor = Exception.class), Spring detects the unhandled exception, issues a ROLLBACK to MySQL InnoDB, and restores Kamal's balance back to LKR 50,000.00.

Question B: Why is recordFailure in a separate class with REQUIRES_NEW?

Answer:
There are two vital technical reasons: 1. Transaction Boundary Separation (REQUIRES_NEW): When the transfer fails, the transfer transaction is marked as rollback-only. If recordFailure participated in the same transaction (REQUIRED), any record saved to bank_transactions would be discarded during the rollback. Propagation.REQUIRES_NEW instructs Spring to suspend the active rolling-back transaction, create a brand-new database transaction, insert the FAILED audit record, and commit it independently. 2. Spring AOP Dynamic Proxy Mechanics (Avoiding Self-Invocation): Spring manages transactions by wrapping beans in dynamic proxies. When an external class calls a method on a bean, the call goes through the proxy interceptor which initiates the transaction. If a @Transactional(propagation = Propagation.REQUIRES_NEW) method is defined in the same BankService class and invoked as this.recordFailure(...), the invocation bypasses the Spring proxy entirely (direct local method dispatch). As a result, the REQUIRES_NEW annotation is ignored. By placing recordFailure in an external service (TransactionAuditService), Spring's proxy intercepts the call and starts the independent transaction as intended.

Question C: Why does debit use UPDATE ... WHERE balance >= :amount instead of reading the balance first?

Answer:
In concurrent environments, the naive two-step approach: 1. SELECT balance FROM customers WHERE account_number = ? 2. if (balance >= amount) UPDATE customers SET balance = balance - amount ...

suffers from a classic Race Condition (Time-of-Check to Time-of-Use / TOCTOU): - Suppose Account 100001 has LKR 10,000.00. - Thread A reads balance = LKR 10,000.00 and decides to transfer LKR 8,000.00. - Concurrently, before Thread A updates, Thread B reads the same balance = LKR 10,000.00 and decides to withdraw LKR 8,000.00. - Both threads conclude there are sufficient funds. Thread A deducts LKR 8,000.00 (balance becomes 2,000.00). Thread B then deducts LKR 8,000.00 (balance becomes -6,000.00). - The account is now overdrawn, and money was duplicated.

By implementing debit as a single atomic SQL statement:

UPDATE customers SET balance = balance - :amount WHERE account_number = :accountNumber AND balance >= :amount;

MySQL InnoDB locks the specific row and evaluates the balance condition at the exact moment of update within the database engine. If the balance is insufficient, the WHERE condition matches 0 rows. The query returns an update count of 0, allowing the application to throw an InsufficientBalanceException with zero risk of concurrency anomalies.

9.1 The Unsafe Demonstration (Propagation.SUPPORTS)

  1. In BankService.java, the annotation on transfer() is temporarily changed: java // @Transactional(rollbackFor = Exception.class) @Transactional(propagation = Propagation.SUPPORTS) public BankTransaction transfer(TransferRequest request) { ... }
  2. When a transfer of LKR 1,000.00 from Kamal to Saman is executed with "Simulate a system failure" enabled:
  3. Sender (Kamal): Balance drops from LKR 50,000.00 to LKR 49,000.00 (debit committed).
  4. Simulated Crash: Exception thrown after debit.
  5. Receiver (Saman): Never receives the funds (remains at LKR 10,000.00).
  6. Total Bank Balance: Decreases from LKR 85,000.00 to LKR 84,000.00.
  7. Observation: The money vanished from existence because the auto-committed withdrawal was not reversed!

9.2 Restoration & SQL Data Repair

To restore transactional safety, BankService.java is restored to:

@Transactional(rollbackFor = Exception.class)
public BankTransaction transfer(TransferRequest request) { ... }

When repeated with rollback enabled, the transaction intercepts the failure and executes ROLLBACK. Kamal's balance remains unchanged at LKR 50,000.00 and Saman remains at LKR 10,000.00.
